# Skill-owned deterministic tools: inventory, colocate, compose, prove

## The problem to solve

JSHack has increasingly capable agent guidance in `.agents/skills/`, but many of the executable tools those skills describe still live in a flat root `tools/` directory. The agent must reconstruct the relationship between a capability, the tool that implements it, the permitted effects, and the evidence that proves it worked. The tool/script boundary is therefore less discoverable and harder to evolve than it should be.

**Desired result:** each coherent agent-facing capability packages its own executable scripts (`scripts/`), operational guidance (`SKILL.md`), and optional deeper references/fixtures. Its SKILL.md explains **when to invoke tools, how to compose them, what decisions their outputs support, and how to verify results**—not just a command listing.

This is a relocation/agent-operability effort, **not** a gameplay refactor, another universal authoring framework, or a requirement to document every possible future workflow.

## Verified starting points (recheck HEAD before editing)

It trains in a **simplified mini-simulation**, not the real ECS scheduler.
- `tests/agentTools.test.mjs` imports root-`tools/` modules directly. `deno.json`, `AGENTS.md`, `tools/AGENT_PLAY.md`, architecture docs, scripts, and CI may contain hard-coded paths.
- Existing `deno task headless`, `agent:play`, `guard:tools`, `guard:architecture`, `guard:events`, `audit:*` entry points are established interfaces. Preserve their names/behavior.
- #156 was deliberately closed as a *broad standalone skills-coverage initiative*. **Do not reopen/recreate that scope**: improve real, current capabilities, and let future content-authoring skills evolve incrementally during feature work, per `AGENTS.md`.

## Ownership policy (make this explicit in AGENTS.md)

Classify **every current entry under `tools/`** using evidence of actual usage, not names alone:

| Classification | Action |
| --- | --- |
| **Skill-owned agent utility** | Move the implementation into its owner skill's `scripts/`. |
| **Shared agent utility** | Choose **one** cohesive canonical skill owner; other skills link to/use that path; no copies. |
| **General repository/CI/developer or application tooling** | Keep outside `.agents/` when it has a legitimate independent audience/lifecycle; document why. |
| **Obsolete/superseded/unclear** | Document evidence and disposition; **do not delete** just because static search suggests it is unused. |

Prefer colocation over a directory of empty instruction wrappers. Do not turn each CLI into a trivial one-tool skill if several naturally comprise one capability. Do not force browser apps, release packaging, audio asset tools, or unrelated developer utilities under `.agents/` merely to maximize relocation count.

An owned script may be called by multiple other skills. Ownership determines the **single implementation and maintenance home**, not exclusive permission to invoke it.

### Stage 1 — inspection/architecture capability

Migrate eligible inspection scripts currently routed by `agent-tools` into the skill's `scripts/`. Update their imports, repo-root resolution, tests, invocation examples, task aliases and references.

Make `SKILL.md` task-oriented: map typical questions to the minimum tool, show output interpretation and escalation to the next tool. Example: target discovery → content-ID provenance → event producer/consumer inspection → scheduler placement → architecture guard. Tools remain read-only unless explicitly identified otherwise.

### Stage 2 — runtime proof capability

Migrate eligible `runtime-tools` scripts in one or more bounded groups, with their related documentation/references.

Preserve the real scheduler, content registration, WorldView, JSONL agent contract, deterministic seeds, action traces, output formats, and performance measurement meaning. **Don't regress the recent headless-runner content-install initialization.** Ensure the relocated scripts resolve game imports reliably and work when invoked from the repo root; do not require `cd .agents/...`.

Document an agentic proof path: seeded reproduction → observation of game state → action/replay trace → focused regression test → comparable performance evidence where relevant. A successful process exit is **not** gameplay proof.

### Stage 3 — specialized monster neural-network training

Create or extend a cohesive `monster-ai-training` skill and colocate `tools/trainAI.js` under its `scripts/`. Do not touch `tinyMLP.js`, `policyAction.js`, or committed `aiWeights.js` except for demonstrably necessary path fixes (weights themselves must **not** change in this issue).

Its guide must explain:

- Tactical vs caster policy, input features, action outputs, model/runtime connection and existing weights.
- Parameters (`--tier`, `--gens`, `--lambda`, `--sigma`, `--trials`, `--turns`, `--seed`, optional `--out`).
- That training is stochastic-search **with a seeded PRNG**, and the mini-sim fitness is a *proxy*, not demonstrated real-game AI quality.
- Safe baseline/candidate procedure: reproducible train/test seeds, held-out evaluation or comparable seeds, behavioral observations in the real game, and explicit regression criteria.
- That `--out` can mutate the weights file; weight adoption must be an **explicitly approved separate step**.

**Important smoke-test trap:** the existing trainer does **not** implement a safe `--help` early exit; treating `--help` as a generic probe can accidentally launch the default 500-generation training. Use `deno check` or a verified **bounded** training invocation (e.g. `--gens 1 --lambda 1 --trials 1 --turns 4 --seed 42`, **without `--out`**) and check output determinism before/after relocation. Do not run the default long trainer, overwrite weights, or present training fitness as validated gameplay.

### Stage 4 — remaining eligible tools and accurate composition

Continue migrating remaining tool families that have a **justified** skill owner, in coherent batches. If a tool should remain in `tools/`, retain it there and state the reason in the ownership matrix; do not leave a half-migrated copy.

Update affected SKILL.md guides to explain tool **interop** and hand-offs:
- Inspect/discover → identify canonical code/IDs/events.
- Implement via the existing code/content contracts (not via a new framework).
- Prove actual behavior via runtime tool(s).
- Validate invariants with appropriate guards/tests.
- Capture only **proven** new reusable knowledge in the smallest owning skill.

Use concise skills with optional `references/` for deep material. Preserve skill names and discoverability; consolidate overlapping guidance where truly redundant instead of inflating the skill count.

## Compatibility and engineering constraints

- **Move, don't fork.** One canonical executable per tool; no parallel implementations or substantial forwarding copies. Use thin compatibility entrypoints **only where existing non-skill consumers cannot be moved**; record each retained shim and a reason.
- Keep established `deno task` commands and tested CLI flags/results stable. Redirect tasks to new script locations as necessary.
- Tools run correctly from repo root; use reliable module-relative URL resolution for imports/assets and explicit repo-root paths where needed. Beware the changed `../src/` depth after relocation.
- Keep scripts JavaScript/ESM/Deno, preserve deterministic simulation and narrow permissions. A tool being inside `.agents/` is **not** permission to mutate the game or execute with broader rights.
- Respect `AGENTS.md`: no unrelated gameplay/content/stat/model changes, cross-layer violations, new world-attached state, new string-only events, broad cleanup, or formatting.
- Fix all importers and discoverability links. Include `tests/agentTools.test.mjs`, task wiring, markdown commands, CI, existing docs and any automated invocation of `tools/`. Don't blindly rewrite human-readable historical notes or third-party vendored text.
- Do **not** introduce a universal skill runner, execution framework, new dependency, or mandatory orchestration layer. Skills describe composition; existing CLIs do the deterministic work.
- Validate edge cases such as standalone script execution, loading as an imported module, handling cwd different from script location where supported, relative path arguments, machine-readable/stdout contracts, and reproducible output.
