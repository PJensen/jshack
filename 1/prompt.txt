## Problem

Eating your own pet correctly triggers a **horrifying** `pet_corpse_desecration` offense, 48 desecration stacks, wrath debt, and an ominous deity reaction. Yet the player can walk away with **no divine lightning**, even after wrath escalates.

This is a **strike-delivery defect**, not a request for more punishment types, new deity architecture, or revised spirit graphics.

## Code-grounded thesis (verify with a seeded end-to-end trace)

- `src/rules/content/items/usePayloads.js` emits `corpse:desecrated`; `src/rules/systems/deitySystem.js` records the offense and raises the deity's wrath.
- The vendored `src/lib/deity-js` submodule's `Deity._checkEvents()` already emits a `wrath` callback **every deity tick** while `precise.wrath > thresholds.wrath`.
- `wireDeityMiracles()` in `deitySystem.js` initializes `cooldowns.wrath = 0` and rejects callbacks while `(tick - cooldowns.wrath) < 30`. That imposes an unintended **initial 30-deity-tick immunity**. After a successful strike, the same fixed interval blocks further strikes.
- A **separate three-turn post-offense grace period** already exists. Keep it; don't confuse it with the 30-tick cooldown.
- `deity:wrath` already drives canonical divine damage, curse/shock, messages, and lightning via `src/display/fx/boltFxController.js`. The rendering pipeline is not the primary suspect.
- Existing corpse/deity tests prove wrath escalation and no immediate execution, but **do not prove a real strike becomes possible on subsequent player turns**. Some wrath tests manually emit at tick 100, bypassing the start-of-run gate.

**Thesis:** the deity is furious and emitting wrath candidates, but JSHack's fixed gate discards them. Prove or disprove this in an ordinary seeded simulation before modifying behavior.

## GREENLIGHT-FAST implementation

1. **Trace first.** Reproduce: fresh run → eat owned pet corpse → record deity mood/threshold, grace turn, emitted `wrath` callbacks, accepted `deity:wrath` events, and actual lightning. Check active-patron eligibility where applicable; distinguish threshold failure from cooldown suppression.
2. **Fix strike eligibility only, with CONSERVATIVE odds.** Remove the unintended initial 30-tick immunity. **Turn 0 = offense; turns 1–3 = guaranteed grace (no lightning rolls); turn 4 = first eligible roll.** When the deity's actual wrath exceeds its configured threshold, roll **once per eligible committed player turn** via `world.rand()`. Use a monotonic curve normalized from that deity's threshold: **~1% per turn just above threshold, rising to a HARD CAP OF 10% at maximum wrath.** This supersedes/rejects the earlier proposed **15–60%** curve as far too punitive. No rolls below threshold; no guaranteed strike by a given turn; no per-frame or repeated-callback rolls.
3. **Recovery only after a successful strike.** Following actual lightning, suppress further rolls for **four committed player turns**, then resume the conservative per-turn rolls if wrath still exceeds threshold. A missed roll must **not** trigger or reset recovery. Do not retain a blanket 30-tick cooldown; do not produce consecutive lethal hits. Keep any existing major-wrath safeguards and document the odds/recovery alongside the implementation.
4. **Reuse current punishment.** Once selected, route through the existing `deity:wrath` damage/status/event path and lightning VFX. Preserve severity scaling, wrath debt behavior, and the existing three-turn grace. Do not add curses, hazards, deity event types, or spirit-wisp behavior.
5. **Prove it.** Focused deterministic tests should cover ordinary play with low wrath (no new lightning), pet desecration raising wrath, no strike during grace, a nonzero strike chance starting on turn 4 at high wrath, higher strike frequency at extreme wrath, one roll/strike per committed turn, recovery after a successful strike, and a genuine `deity:wrath` event that reaches existing lightning wiring. Exercise seeded sequences rather than invoking `deity._emit('wrath', { tick: 100 })` as the only proof.
