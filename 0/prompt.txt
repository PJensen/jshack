This is a productive exchange. You pushed Codex away from inventing architectural problems and toward understanding the actual ECS machinery.

I particularly agree with your instinct about separating the overloaded `ai` phase into decision-making and tactical resolution. That gives the architecture a meaningful boundary instead of relying on increasingly delicate system ordering.

But there's one architectural issue I'd challenge before proceeding.

### `TacticalIntent` is not the same thing as a tactical proposal

You've established that `world.add()` replaces an existing component.

Suppose chase proposes `flank` and the neural policy proposes `kite`. If both write to the actor's singleton `TacticalIntent`, the second proposal overwrites the first before arbitration even happens.

We've recreated the original problem, just one level higher.

The distinction should be:

Tactical decision producers

Chase · Neural policy · Contextual behaviors

Candidate evaluation / arbitration

Evaluate priorities, constraints, and existing objectives

Selected TacticalIntent

One authoritative objective per actor

Canonical action intents

Move · CastSpell · RangedAttack · etc.

That doesn't necessarily require another component or complicated proposal framework. A deterministic decision function could evaluate candidates and write the selected objective once.

### Two other considerations

The six tactical objectives aren't all equivalent. Pursue and retreat are broad movement strategies. Flank and rally imply relationships with other actors. Kite represents range management, while hold represents a positional constraint. Their lifetimes and invalidation rules will differ. A common component is sensible, but it shouldn't obscure those distinctions.

A new `tactics` phase is justified if it establishes real ordering guarantees. Not simply because `ai` contains 18 systems. The boundary should ensure every relevant proposal is available before selection and all canonical action intents are emitted before validation.

And I strongly agree with your objection to calling ECS component replacement an ownership conflict. Entity ownership, decision authority, and proposal provenance are separate concerns.

One visibility qualification: the tactical implementation described by Codex isn't yet visible in the GitHub snapshot I can access, so I'm evaluating the architecture in your transcript rather than claiming I've verified those local changes.

My position: Keep the direction. Add the explicit distinction between candidate objectives and selected objective. That's the one place where the proposed architecture could accidentally reproduce the exact defect we're trying to eliminate.
