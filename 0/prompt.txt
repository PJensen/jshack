# One Sparse Underworld Implementation Plan

## Summary
Implement one continuous underworld, not separate durable dungeons. `currentDepth` remains the canonical vertical coordinate: `0` is overworld, positive values are depth into the underworld. Entrances seed authored underground regions at matching overworld `x/y`, and deeper stairs continue by increasing `currentDepth`.

`dungeonId` should not define topology. Use `templateId` or provenance metadata only for generation, quest targeting, and debugging.

## Core Changes
- Add entrance-authored underworld metadata.
  - Create a `DungeonEntrance` component for overworld stair entities.
  - Fields: `templateId`, `label`, `type`, `length`, `biome`, `monsterTier`, `lootTier`, `questId`, `targetDepth`.
  - Tavern stair targets `currentDepth: 1` below the tavern.
  - Graveyard stair targets `currentDepth: 1` below the graveyard.
- Preserve `DungeonState.currentDepth` as the authoritative Z/depth coordinate.
  - Do not demote it to compatibility state.
  - Add `activeTemplateId` or `activeRegionTemplateId` only as generation/provenance metadata.
  - Future deeper authored dungeons use `currentDepth: 2`, `3`, etc. with the same `x/y` world coordinate space.
- Refactor floor identity from depth-only to sparse underworld slice keys.
  - Use keys that include `currentDepth` plus generated chunk/region coordinates.
  - Floor cache, explored memory, destroyed tiles, wet tiles, and restored entities must not assume all depth-1 entrances share the same generated floor.
- Generate authored regions by entrance anchor.
  - Region footprint starts at the entrance’s overworld `x/y` on `currentDepth`.
  - `length` controls random-walk room/footprint growth.
  - `type`/`biome` selects profile, monster filters, feature pools, density, and loot tier.
  - Regions at the same depth can coexist in different sparse `x/y` areas.

## Starter Content
- Tavern basement:
  - `templateId: "tavern_basement"`
  - Depth 1, 2-3 rooms, cellar/basement type.
  - Rat-heavy monsters, torches, barrels/crates/chests, low loot.
  - Rat infestation quest targets this template/region, not generic depth 1.
- Graveyard crypt:
  - `templateId: "graveyard_crypt"`
  - Depth 1, 5-6 dense rooms, crypt/catacomb type.
  - Skeleton-heavy monsters, urns, sarcophagi, chests.
  - Book quest target spawns here, not generic depth 1.
- Keep the design open for deeper templates:
  - Example: tombs/caves/mines may place downward stairs to `currentDepth + 1`.
  - Deeper continuation remains the same underworld, not a nested dungeon id.

## Transition Behavior
- Descending an overworld entrance:
  - Read `DungeonEntrance`.
  - Load or generate the sparse region at `{ depth: targetDepth, anchorX, anchorY }`.
  - Place the matching up-stair at the same `x/y` coordinate when possible.
- Ascending:
  - From depth 1, return to the matching overworld entrance position.
  - From deeper levels, decrement `currentDepth` while preserving coordinate identity.
- Generic stairs without entrance metadata continue using existing depth behavior, but should route through the same coordinate-keyed transition path.

## Tests
- Add sparse identity tests:
  - Tavern and graveyard depth-1 regions are distinct despite sharing `currentDepth === 1`.
  - Revisiting each restores its own entities, explored state, destroyed tiles, and wet tiles.
- Add transition tests:
  - Tavern stair descends to tavern basement and ascends back to tavern.
  - Graveyard stair descends to crypt and ascends back to graveyard.
  - A deeper authored region can produce stairs to `currentDepth + 1`.
- Add content/quest tests:
  - Rat quest content appears only in tavern basement.
  - Book quest content appears only in graveyard crypt.
  - Monster/theme filters match basement and crypt expectations.
- Run:
  - `deno task check`
  - `deno test --allow-read --no-check`

## Assumptions
- `currentDepth` is the real Z/depth coordinate.
- There is one underworld coordinate space.
- `templateId` is useful for generation and quest semantics, but mining can erase any meaningful boundary between authored regions.
- This implementation should prioritize the coordinate foundation first, then layer the two starter regions on top.
