# Rift Return Options

## 1. Stair Return
Use normal `stair_up` as the rift exit.

- Implementation: pass the rift opening portal position as `stairPos` when entering the rift.
- Result: level 1 gets a `stair_up` exactly where the player arrives.
- Pros: easiest, uses existing transition code, preserves retreat, low risk.
- Cons: least flavorful; a stair inside a rift feels a bit mundane.

## 2. Return Rift
Use a paired rift portal inside the rift.

- Implementation: spawn a `rift_portal`-looking return entity on rift level 1, probably at the entrance tile.
- Interaction: same visual language as the opening rift, but action exits back to origin instead of entering.
- Pros: thematically clean; “rift is a pairing” is easy to understand.
- Cons: needs a small new return action/path so it does not re-enter the rift or confuse `RiftPortal` semantics.

## 3. Return Portal
Use the existing return portal concept.

- Implementation: spawn a `return_portal` entity inside the rift and route it through existing `portal:return`.
- Pros: likely reuses existing portal return wiring.
- Cons: can conflict conceptually and technically with homecoming/hearthstone/resurrection return portals; less clean for rifts.

## Recommendation
Pick **Option 1** for the immediate regression fix. It is the safest way to restore return behavior now.

Then consider **Option 2** as the better long-term rift flavor: a paired rift return, possibly spawned at entrance or after boss death.
